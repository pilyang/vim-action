# 오퍼레이터 키는 ANSI 고정 키코드 — QWERTY 계열 가정

## 결정

편집 시퀀스의 오퍼레이터 키는 **ANSI 고정 키코드**로 낸다: `Cmd-X` = `kVK_ANSI_X`(7), `Cmd-C` = `kVK_ANSI_C`(8). 현재 레이아웃에서 `x`/`c`를 내는 키코드를 역조회하지 않는다.

이는 **QWERTY 계열 레이아웃 가정**이며, 비-QWERTY(Dvorak, AZERTY 등)에서는 `d`/`c`/`y`/`x`가 엉뚱한 `Cmd-` 단축키로 해석되는 한계를 동반한다. 릴리스 게이트(M3 단계 4) 해제 시 안전판 필요 여부를 재검토한다.

## 배경·근거 (왜)

M2까지 합성한 키는 화살표뿐이었고, 화살표 키코드(123~126)는 **레이아웃 무관 고정값**이라 이 문제가 존재하지 않았다 ([20260726_motion-keystroke-mapping-contract.md](20260726_motion-keystroke-mapping-contract.md)). 편집이 처음으로 문자 키를 합성하면서 레이아웃 의존이 출력측에 들어온다.

macOS는 `Cmd-` 단축키를 키코드가 아니라 **그 키가 레이아웃에서 내는 문자**로 매칭한다. 즉 Dvorak 사용자에게 키코드 7은 `x`가 아니라 다른 문자이고, `Cmd-X`가 잘라내기가 아닌 다른 명령(볼드 등)이 될 수 있다. 입력측 `KeyTranslator`는 이미 `UCKeyTranslate` + ASCII-capable 레이아웃으로 레이아웃 인식이므로([20260716_cgevent-key-translation-ascii-layout.md](20260716_cgevent-key-translation-ascii-layout.md)) 비대칭이 생긴다 — 입력은 정확히 읽고 출력은 가정한다.

그럼에도 고정을 택한 이유는 **범위 대비 비용**이다. 역조회를 하려면 매퍼가 순수 함수를 그만두고(레이아웃 데이터 주입 + 캐시 무효화 계층) 골든 테스트가 레이아웃 조건부가 된다. 이것은 편집 실행 본체와 독립적인 별개 작업이고, 지금 섞으면 이번 단계의 검증 가능성이 떨어진다. 한계를 문서로 고정해 두면 나중에 매퍼 내부 상수 2개 교체 + 주입 계층 추가로 되돌릴 수 있다.

프로젝트에 이미 `QwertyLayoutCondition`(테스트용 레이아웃 판정)이 있어, 안전판을 붙일 때 재사용할 판정 로직은 존재한다.

## 검토한 대안

- **현재 레이아웃에서 `x`/`c` 키코드 역조회**: 정확하지만 매퍼의 순수성이 깨지고 주입·캐시 무효화가 단계 1 범위에 추가된다. 이연(한계 해소가 필요해지면 이 문서를 supersede).
- **delete/change를 레이아웃 무관 `Delete` 키로**: 절반은 회피되지만 `d`/`x`가 클립보드에 실리지 않아 v1의 "시스템 클립보드 = 무명 레지스터" 설계(`p`와의 정합)가 깨진다. 기각.
- **비-QWERTY 감지 시 편집 비활성화**: 지금 넣기에는 이르다 — 실제 피해 범위(어떤 앱에서 어떤 단축키로 오작동하는지)를 도그푸딩 전에 알 수 없다. 릴리스 게이트 해제 시점의 판단으로 이연.

## 영향 범위

- `VimAction/EditKeyMapper.swift`의 `cut`·`copy` 상수 — 이 파일에서 레이아웃 의존은 이 둘뿐이다.
- 골든 테스트는 레이아웃 무관하게 성립한다(기대값도 같은 ANSI 키코드) — 실기기 오작동은 도그푸딩에서만 드러난다.
- 릴리스 게이트(M3 단계 4) 해제 판단 항목에 "비-QWERTY 안전판" 추가.
