# 탭 들여쓰기의 ^·I는 Chromium 계열에서 0으로 퇴행 — 수용

## 결정

[^·I 3타 조합](20260726_word-forward-first-nonblank-multi-stroke.md)의 수용 엣지에 4번째를 추가하고 매핑은 유지한다: **선행 공백이 탭인 줄에서는 Chromium 계열(브라우저·Electron) 앱의 `^`·`I`가 `0`과 동일하게 동작한다** (첫 비공백이 아니라 줄 맨 앞 착지).

## 배경·근거 (왜)

3타 조합 적용 후 실기기 검증(2026-07-26)에서 발견됐다. 스페이스 들여쓰기는 어디서나 정확한데, 탭 들여쓰기는 브라우저에서 `0`처럼 동작했다.

- **네이티브 텍스트 시스템(TextKit)은 정확하다** — `NSTextView`에 `moveToBeginningOfLine → moveWordRight → moveWordLeft`를 직접 호출한 실측: 스페이스 4개·탭 1개·탭 2개·탭+스페이스 혼합 모두 첫 비공백 인덱스에 정확 착지.
- Chromium 계열은 단어 세그먼테이션이 달라 **탭 런을 별도 경계 토큰으로 취급**한다: `Opt-→`가 탭 뒤에서 한 번 멈추고 `Opt-←`가 탭 앞으로 되돌아가 순효과가 col 0이 된다.
- 두 세그먼테이션 모델을 동시에 만족하는 **고정 시퀀스는 존재하지 않는다**: Chromium 탭 케이스를 맞추려 `Opt-→`를 추가하면 스페이스 케이스가 둘째 단어로 깨진다. 매퍼는 무상태(줄 내용을 모른다)라 콘텐츠 조건 분기도 불가하다.
- 실패 모드가 온화하다: `0`과 동일 = 3타 개선 **이전과 같은 동작으로의 퇴행**이지 오동작이 아니다.

정확한 해결(텍스트를 읽어 첫 비공백 오프셋 직접 계산, 앱 세그먼테이션 무관)은 기존 방침대로 M5 AX 어댑터의 몫이다.

## 검토한 대안

- **`Opt-→` 추가(4타)로 탭 케이스 대응**: 스페이스 들여쓰기·비들여쓰기 줄이 깨진다(둘째 단어 착지). 기각.
- **앱별 시퀀스 분기**: 매퍼가 앱 정체를 알게 되어 순수 매핑 계약이 깨지고, M4 프로파일·M5 AX가 담당할 축을 선점한다. 기각.

## 영향 범위

- 코드 변경 없음 — 현재 매핑 유지의 근거 기록.
- M5 AX 어댑터가 `lineFirstNonBlank`를 정확 구현하면 이 엣지는 자연 해소된다.
