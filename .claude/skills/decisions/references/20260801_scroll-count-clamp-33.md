# 스크롤 카운트 상한 33 — 증폭 어휘의 클램프 우회 봉쇄

## 결정

엔진의 스크롤 반복 출력(`normalCtrlCombos` 분기)에 **스크롤 전용 상한 33**을 둔다. `999 Ctrl-f`는 `.scroll` 액션 33개로 클램프된다. redo(`Ctrl-r`)를 포함한 다른 반복 출력은 기존 `maxCount`(1,000)만 적용받는다.

## 배경·근거 (왜)

M3 단계 4 킬스위치 회귀 검증이 실증한 문제다: [카운트 클램프 1,000 하향](20260731_count-clamp-lowered-to-1000.md)의 목적은 "최악 폭주 총량 제한"인데, 스크롤은 **액션 1개가 키스트로크 수십 타로 증폭되는 유일한 반복 출력**이라(fullPage = `↓`×30, [화살표 반복 결정](20260730_scroll-arrow-repetition.md)) 이 상한을 사실상 우회한다 — `999 Ctrl-f` = 29,970 스트로크 ≈ 클램프가 막으려던 `9999j`의 3배다.

실기기에서 이것이 문제가 되는 방식: 게시(초당 ~4천 타)가 대상 앱 소비(TextEdit ~초당 370타)보다 빨라, 중단 래치가 게시를 즉시 끊어도 **이미 게시된 백로그는 회수할 수 없다**. 스크롤 폭주 중 킬스위치를 눌러도 백로그가 소진될 때까지 수 초~수십 초 스크롤이 이어지는 체감이 관찰됐다. 상한 33(fullPage 30타 기준 ≈990타 = `maxCount` 등가)은 최악 백로그를 다른 어휘와 같은 수준으로 되돌린다.

값 33이 어댑터의 30타 확장에서 유도된 것은 인지하고 수용한다 — 엔진 순수성 관점에서는 어댑터 지식이지만, `maxCount` 1,000 자체가 "일상 사용 상한"이라는 실행 계층 감각으로 정해진 값이다(같은 결정의 기준 전환 참조). 어댑터의 스트로크 확장 값이 바뀌면(M4 프로파일 조절값 예정) 이 상한도 재검토한다.

잔여 수용: 클램프 후에도 백로그 자체(게시>소비 비대칭)는 남는다 — 33×30 = 990타의 꼬리(~수 초)는 수용하고, `chunkInterval` 튜닝은 M4 카드로 이월한다. 이 수용은 [게이트 해제 심사](20260801_release-block-gate-lifted.md)에 기록된다.

## 검토한 대안

- **어댑터에서 클램프**: 증폭 지식이 있는 자리라는 점은 맞지만, 어댑터는 반복 액션을 개별로 받아 "몇 번째인지"를 세는 상태가 필요해진다. 카운트 의미론은 엔진 소관이라는 기존 구조(`maxCount`·픽스처)에 얹는 쪽이 작다. 기각.
- **`Ctrl-d/u`(half, 15타)에 별도 상한 66**: 정밀하지만 상한이 두 개가 되고, half의 33×15 = 495타는 이미 충분히 작다. 단일 값 유지. 기각.
- **수용 + 문서화만**: 코드 무변경이지만 "킬스위치를 눌러도 수십 초 스크롤"은 안전장치 신뢰를 깎는 실측된 체감이다. 클램프 1줄로 최악치가 1/30이 되므로 기각.
