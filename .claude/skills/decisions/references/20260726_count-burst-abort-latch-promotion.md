# 카운트 폭탄 실측 — 실행 중단 래치 M3 승격

## 결정

실행 중단 래치(게시 큐의 잔여 합성 이벤트를 폐기할 수단)를 **M3 단계 4 범위로 승격**한다. M2에서 "실측 후 판단"으로 이연했던 항목이며, 승격 기준(폭주 ≈1초 이상)을 실측이 충족했다. 구체 설계는 단계 4에서 확정하되, 실측이 시사하는 방향은 **청크 게시 + 청크 사이 중단 체크**다 — 폭주 중단·타이핑 순서 역전 방지·이벤트 드랍 완화를 한 설계로 잡을 여지가 있다.

## 배경·근거 (왜)

M3 단계 0 실기기 실측 (TextEdit 12,000줄 파일, DEBUG 빌드):

- **소요 시간**: `100j` 1초 이내 정상, `999j` 1~3초 완주, `9999j`(클램프 상한)는 **심한 렉 + 비치볼 후에야 완주** — 수 초 이상의 중단 불가 폭주로 승격 기준 충족. `w`가 3타 조합이 되어 실제 부담은 카운트×3까지 커질 수 있다.
- **킬스위치 한계 실증**: `9999j` 직후 콤보 발동 시 **발동 자체는 즉시**(메뉴바 글리프 즉각 전환)지만 **이미 게시된 이벤트는 끝까지 소진**된다. 코드 구조와 일치 — 게시 직렬 큐는 sink 클로저에 캡처된 로컬이라 컨트롤러가 핸들을 갖지 않고, 취소 API 호출이 없다 (`EventTapController.swift:157-162`). 킬스위치는 "새 키 가로채기"만 막는다.
- **순서 역전 실증**: `9999j` 직후 `i`+`abc` 타이핑 시 a·b·c가 캐럿 도착 전 **중간중간 흩어져 삽입**됐다. 버스트 중 사용자 입력이 문서를 오염시킨다 — 단순한 지연 문제가 아니라 데이터 정합성 문제이며, "새 입력 시 잔여 큐 폐기" 의미론의 직접 근거다.
- **배달 보장 붕괴 (Notion)**: `999j`급 버스트에서 998·999행 근처 정지가 종종 발생 — 합성 이벤트 1~2건이 앱 측에서 소실된다. 대량 버스트의 배달은 앱에 따라 best-effort다. 청크 게시(속도 완화)가 이것까지 완화할 가능성이 있어 래치 설계와 결합해 검토한다.

## 검토한 대안

- **래치 없이 카운트 클램프만 축소 (9,999 → 수백)**: 폭주 총량은 줄지만 중단 수단 부재·순서 역전은 저카운트에서도 잠재하고, 클램프는 엔진 계약이라 실행 계층 문제의 해법으로 부적절. 래치와 별개로 클램프 값 재검토는 단계 4에서 함께 다룰 수 있다.
- **수용 (래치 없음)**: M2 시점의 기본안. 9999j가 빠르게 소진됐다면 유지했겠지만, 실측이 기준을 초과해 기각.
