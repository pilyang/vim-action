# 번들 기본값은 병합 계층이 아니라 파일 단위 시딩

- **결정일**: 2026-08-02

## 결정

번들 기본값(config.yaml + Slack·Notion 기본 프로파일)은 앱 안에 살면서 사용자 파일 아래에 깔리는 **병합 계층이 아니라**, 앱이 `~/.config/vim-action/`에 **복사해 넣는 초기값**이다.

- **시딩 단위는 파일**: 각 파일이 없을 때만 복사하고, **이미 있으면 내용을 보지 않고 그대로 둔다**. 이후 버전이 추가하는 새 기본 프로파일은 이 규칙으로 들어온다.
- **읽기는 사용자 파일 1계층**이다. 설정 계층에 병합은 없다 — `config.yaml` 하나, `profiles/<bundle-id>.yaml` 하나가 각각 그 자체로 최종값이고, "기본값"은 값의 **부재**로 표현된다(scroll 15/30, 매퍼 키 테이블 등 코드 상수).
- 따라서 값의 **출처 계층 개념이 사라진다** — 설정 UI가 표시할 "이 값을 정한 계층"이 없다.

## 배경·근거 (왜)

- **사용자가 기본값을 지울 수 있어야 한다** (사용자 결정). 병합 계층이면 사용자는 아래 계층의 항목을 *덮을* 수만 있고 *없앨* 수는 없다. 이 비대칭이 실제로 막힌 지점: `actions:`의 v1 값은 `disabled`뿐이라([disable은 매핑 값 결정](20260802_profile-disable-via-mapping-keyword.md)), 번들 Slack 프로파일의 `open_line: disabled`를 사용자가 되켤 표현이 아예 없었다. 시딩이면 자기 파일의 그 줄을 지우면 끝이라 스키마에 `enabled` 같은 되켜기 어휘를 만들 필요가 없다.
- **파일이 SSOT, 사용자가 편집자**라는 [설정 루트 결정](20260801_config-root-dot-config.md)의 전제와 더 곧다. 사용자가 여는 파일에 실제로 적용 중인 값이 전부 적혀 있다 — 병합이면 "내 파일엔 없는데 어딘가에서 켜지는" 값이 생긴다.
- **설정 계층이 통째로 단순해진다**: 병합·계층 출처(`ConfigLayer`)가 사라져 파서 결과가 곧 최종값이다.

## 파급 (수용)

**이후 버전이 기존 파일의 내용을 갱신하지 못한다.** 새 위험 앱을 번들 `config.yaml`의 off 목록에 추가해도, 이미 `config.yaml`을 가진 사용자에게는 반영되지 않는다 — 그 사용자는 새 앱에서 개입이 켜진 채로 만나게 된다. 파일 단위 시딩이라 **새로 추가되는 프로파일 파일**은 들어오지만, 기존 파일 **안의** 항목은 못 들어온다.

부수 효과로, 사용자가 지운 프로파일 파일은 다음 실행에 부활한다 — 프로파일을 안 쓰려면 파일을 지우는 게 아니라 내용을 비우거나 `config.yaml`에서 그 앱을 off한다.

필요해지면 "새 기본값이 생겼다" 알림이나 마이그레이션을 additive로 얹는 축이며, 이 결정과 충돌하지 않는다.

## 검토한 대안

- **병합 계층 유지 + `actions`에 `enabled` 값 추가**: 기본값이 앱 업데이트로 계속 갱신되고 사용자 파일은 자기 차이만 담아 짧게 유지된다는 이점이 크지만, "내 파일에 없는 설정이 적용된다"는 모델과 되켜기 어휘 추가 비용에서 밀려 기각 (사용자 결정).
- **루트 디렉터리 단위 시딩** (`~/.config/vim-action/`가 없을 때만 전체 복사): 지운 파일이 부활하지 않아 사용자 소유가 더 완전하지만, 이후 버전이 추가하는 기본 프로파일이 기존 사용자에게 **영영** 안 가서 기각 (사용자 결정).
