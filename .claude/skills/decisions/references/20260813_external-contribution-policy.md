## 결정

외부 기여는 **이슈 우선(issues-first)**: 버그 리포트·기능 요청은 환영하고, PR은 이슈로 사전 논의를 거친 뒤에만 받는다 (오타·문서 수정은 예외로 직접 수용). 프로젝트가 솔로 개발자 + AI 코딩 에이전트(Claude Code) 체제로 관리된다는 사실을 README와 CONTRIBUTING에 명시하고, AI 생성 PR은 제출자가 직접 테스트하고 설명할 수 있는 경우만 받는다.

## 배경·근거 (왜)

- 공개 릴리스 후 GitHub Community Standards 정비 과정에서 기여 정책이 미정의 상태였다. CONTRIBUTING은 파일 작성보다 "기여를 어디까지 받을지"라는 정책 결정이 본체다.
- 이 앱은 시스템 전역 키 입력을 가로채므로 작은 변경도 파급이 크고, Vim 어휘는 의도적으로 큐레이션되어 있다(KEYBINDINGS.md에 out-of-scope 명시). 사전 논의 없는 기능 PR은 방향이 안 맞아 기각될 확률이 높아, 이슈 선행이 양쪽의 낭비를 줄인다.
- AI 관리 체제에서는 수용된 아이디어가 기여자의 PR 대신 새 구현으로 landing할 수 있다. 이를 숨기면 기여자 기대치가 어긋나므로 투명하게 명시하는 쪽을 택했다.
- 드라이브바이 AI 생성 PR/이슈 스팸은 현재 OSS 생태계의 실제 문제다. 메인테이너가 AI를 쓰는 프로젝트가 AI 기여를 금지하는 것은 모순이므로, "테스트했고 스스로 설명할 수 있을 것"을 기준선으로 잡았다.

## 검토한 대안

- **PR 전면 환영**: 기각 — 아키텍처 불변식(해석/실행 분리, 테스트 seam 규칙)의 학습 비용이 높고, 솔로 리뷰 처리량이 병목이라 이슈 필터 없이는 감당이 안 된다.
- **기여 안 받음**: 기각 — macOS 하위 버전(14·15) 지원 강화가 사용자 버그 리포트에 의존하는 구조이고, README가 이미 이슈 제보를 요청하고 있다.
