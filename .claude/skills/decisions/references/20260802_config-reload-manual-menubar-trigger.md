## 결정

설정 리로드는 파일 감시 자동 감지가 아니라 **메뉴바의 'Reload Config' 수동 트리거**로 한다. "앱 재시작 없이 반영"은 유지되고, "파일 저장 시 자동 적용"만 빠진다. 리로드 실패 시 직전 유효 설정 유지 규칙(20260801 config.yaml 스키마 v1)은 수동 리로드에도 그대로 적용되며, 사용자가 방금 클릭한 자리에서 결과(성공/실패)를 보여준다.

## 배경·근거 (왜)

- 원 결정(20260712)의 근거는 "YAML을 직접 편집하는 사용자가 앱을 재시작할 필요가 없어야 한다"였다. 이 근거는 수동 트리거로도 충족된다 — 자동 감지까지는 요구가 아니었음을 M4 세션 B 착수 시점에 사용자가 확인했다 (파일 저장 → 메뉴바 클릭 한 번이 수용 가능한 워크플로우).
- 파일 감시 인프라가 통째로 빠진다: `DispatchSource.makeFileSystemObjectSource` 배선, 에디터 atomic-save(rename으로 파일 노드가 바뀌어 감시가 끊기는 엣지), 연속 저장 디바운스, profiles/ 디렉토리 다중 감시 — 전부 구현·검증 대상에서 사라진다.
- **`ConfigError` 사용자 가시화가 자연스러워진다**: 파일 통째 파싱 실패(YAML 키 중복 등)는 로그로 부족하고 사용자에게 보여야 하는데, 리로드가 사용자 액션이면 그 직후 피드백으로 보여주면 된다. 자동 감지에서는 백그라운드 실패를 어떻게 띄울지(알림? 배지?)가 별도 설계 문제였다.

## 검토한 대안

- **파일 감시 자동 리로드 (원 결정)**: 기각 — 요구 대비 인프라·엣지 비용이 크고, 실패 가시화가 어렵다. 수동 리로드가 실사용에서 번거롭다고 실증되면 additive로 재도입할 수 있다 (수동 트리거는 그대로 두고 감시를 얹으면 됨 — 재개 조건).
