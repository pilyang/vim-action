# 단어 경계 질의는 **로컬 술어**다 — 오프셋을 만들지 않는다

## 결정

`iw`·`cw` 정확화를 위해 "이 단어가 어디서 시작해 어디서 끝나는가"(오프셋) 질의를 세우지
**않는다.** 대신 Vim이 단어를 가르는 **런**(같은 클래스가 이어지는 구간)을 정의하고, 캐럿
**±1자**만 보는 술어 셋을 `FocusedTextAnalysis`에 얹는다.

런 클래스는 넷이다:

| 클래스 | 범위 |
|---|---|
| `blank` | space·tab |
| `keyword` | ASCII 영숫자와 `_` (Vim 기본 `iskeyword`) |
| `punctuation` | 그 외 ASCII |
| `other` | 비ASCII 전부 |

**개행은 어느 런에도 속하지 않는다**(`nil` = 런 종결자).

질의 셋: `caretRunIsSingleCharacter`(런이 1자인가) / `caretIsAtRunEnd`(캐럿이 런의 마지막
글자인가) / `runClassBeforeLineEnd`(줄 끝일 때 직전 글자의 클래스). 기존
`provesNoWordStartAhead`는 그대로 둔다 — `w`의 3타 반전은 존재 여부만 묻기 때문이다.

## 배경·근거 (왜)

### ① 오프셋을 안 쓰기로 하자 정합 문제가 통째로 사라졌다

세션 2의 인계 메모는 "새 질의를 세울 때 구두점 처리를 macOS `Opt-→`와 맞출지 먼저 정해야
한다"를 열린 문제로 남겼다. 기존 정의가 `Opt-→`보다 좁은 것은 "좁게 보면 정확화를 **포기**하는
쪽으로 틀린다"는 안전 논리였는데, **오프셋을 쓰는 순간 그 논리가 무너진다** — 좁은 정의의
오프셋은 틀린 위치를 정확하게 가리킨다.

[상수 1타 재조립](20260803_constant-stroke-word-refinement.md)을 택하면서 이 문제 자체가
없어졌다. 정확화하는 가지는 클래스와 무관한 `Shift-→`·`Shift-←`를 내고(1자를 잡는 데 단어
개념이 필요 없다), 포기하는 가지는 macOS 시맨틱으로 만든 기존 시퀀스가 그대로 나간다.
**두 정의는 만날 일이 없으므로 일치할 필요가 없다.**

유일한 예외가 `iw`의 줄 끝 `Shift-Opt-←`인데, 거기서만 `keyword`로 한정한다 — 구두점 런
앞에서는 macOS `Opt-←`가 앞 단어까지 넘어가 증명이 서지 않는다
([별건](20260803_line-end-cursor-model-for-word-objects.md)).

### ② 창 가장자리 난점이 사라진다

오프셋 질의였다면 "단어가 창(캐럿 ±256) 밖으로 이어질 수 있다"를 매번 다뤄야 하고, 그 판정을
틀리면 잘린 단어의 절반만 정확하게 잘라낸다. 로컬 술어는 캐럿 양옆 1자만 보는데, 반경 clamp
덕분에 **읽기가 성공한 이상 그 두 자리는 항상 창 안이다**. 창 끝에 닿는 경우는 `windowRange`가
문서 경계에 닿았을 때만 경계로 인정하고, 아니면 답하지 않는다(기존 줄 질의와 같은 규칙).

### ③ 비ASCII를 `keyword`가 아니라 `other`로 둔 이유

보수 방향을 지키기 위해서다. `keyword`에 넣으면 CJK·이모지 위에서 정확화가 **발동해** 틀리고,
따로 두면 이웃과 클래스가 같아 런이 2자 이상으로 세어져 **포기**한다. 이모지가 UTF-16 2단위라
1자 런으로 세어지지 않는 것도 같은 편이다 — 서로게이트 쌍을 단위 하나로 판정할 수 없다는
사실이 자연스럽게 안전한 답을 낸다.

혼자 선 1단위 CJK(`a 한 b`)는 1자 런으로 잡히고, 그것은 Vim과 같다.

### ④ 개행이 런에 속하면 줄이 병합된다

개행을 `blank`에 넣으면 `foo\nbar`의 줄 끝에서 "1자 런"이 성립해 `diw`가 **개행을 지운다** —
두 줄이 합쳐진다. Vim의 `iw`는 개행을 잡지 않는다. 그래서 개행은 런 종결자이고, 줄 끝에서
잡을 것은 개행이 아니라 **직전 글자의 런**이다(③의 별건 결정).

## 검토한 대안

- **`Opt-→`/`Opt-←` 착지점을 모델링한 오프셋 질의**: 현행 3타가 어디에 착지할지 예측할 수
  있게 되지만, ②의 잘린 단어 문제를 매번 다뤄야 하고 Vim 시맨틱과의 차이가 질의 안에 그대로
  남는다. 무엇보다 오프셋의 유일한 용도가 "그만큼 스트로크를 낸다"인데 그것을 이미 기각했다.
- **Vim의 3-클래스(공백/키워드/구두점)만 두고 비ASCII를 `keyword`에 흡수**: 코드는 한 줄
  줄지만 ③의 실패 방향이 뒤집힌다. 기각.
- **`provesNoWordStartAhead`를 런 클래스 기반으로 재작성**: 정의가 통일되는 이점은 있으나 그
  질의는 "공백류 다음의 비공백"이라는 다른 질문에 답하고 있고(구두점 경계를 볼 이유가 없다),
  건드리면 엣지 3의 검증된 표가 함께 흔들린다. 기각 — 정의 일관성만 확인했다.
