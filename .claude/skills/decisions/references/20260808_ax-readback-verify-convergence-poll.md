# 되읽어 검증은 수렴 폴링 — 쓰기 `.success` ≠ 적용 완료 (Notion 비동기 적용 실측)

## 결정

편집 하이브리드의 되읽어 검증(파괴 단계 게시 전 선택 착지 확인)의 형태를 넷으로 확정한다:

1. **재읽기는 신선한 선택 전용 읽기다** — `AXSelectedTextRange`만 읽는 경량 재읽기이며, `AXWindowSnapshot` memo를 절대 재사용하지 않는다(액션당 1회 memo는 쓰기 **전** 값이라 재사용하면 검증이 장식이 된다).
2. **1회 읽기가 아니라 수렴 폴링이다** — 쓴 범위와 일치할 때까지 재읽기를 반복한다. 간격 2ms·총 상한 40ms(실측 수렴 ~10ms의 3~4배 마진)로 시작하는 **도그푸딩 조절값**이며, 상한 도달 = 검증 실패다.
3. **검증 실패는 무동작 스킵 + execute 잔여 중단이다** — 파괴 단계(`Cmd-X`/`Cmd-C`)는 나가지 않고, 그 execute의 잔여 액션도 접는다("`.success` 외 전부 중단"과 같은 default-deny — 불일치는 앱의 범위 정규화·오프셋 공간 불일치 신호라 같은 키 입력 안에서 반복해 얻을 것이 없다). 실패 보고는 아니다(쓰기는 `.success`였고 파괴는 시도 전이다).
4. **로그는 전용 버킷·상시 `.info`·번들 ID 포함이다** — `.illegalArgument` 관측 로그와 같은 규칙·같은 이유: 이 빈도가 Visual 양단 검증 승격과 오프셋 공간 문제 판정의 **사후 회수 데이터**다(`log show --info`).

## 배경·근거 (왜)

- **실측: Notion은 `AXSelectedTextRange` 쓰기가 `.success`를 돌려준 뒤에도 적용이 비동기다.** 값이 바뀌는 쓰기 직후의 되읽기가 ~6ms까지 낡은 값을 돌려주고 ~10ms경 수렴한다(세션 0 diag — write `.success` 후 +0.2/+3.4/+6.4ms 읽기는 옛 선택, +9.9ms부터 새 선택). TextEdit는 즉시 일관. 즉 **즉시 1회 읽기로 설계하면 Notion에서 편집 전부가 상시 헛스킵**된다 — 수혜 밴드 1순위 앱에서 하이브리드가 통째로 죽는 설계다.
- 이 실측은 설계 세션의 순서 안전성 문언도 보정한다: "AX 쓰기는 대상 앱 메인 런루프에서 동기로 끝난 뒤 반환"은 Notion에서 거짓이다. "동기 쓰기 → 게시" 방향이 안전한 근거는 **구조 보장이 아니라 지연 마진**(적용 ~10ms < 게시 소비 ~25ms — 세션 0 실측)이고, 마진이 어긋나는 앱은 이 되읽어 검증이 잡는다 — 검증이 정확성 확인과 적용 확인을 겸하는 이중 역할이 된다.
- 같은 이유로 Visual AX 세션의 상태 갱신 근거("쓰기 `.success` = 게시 확정보다 강함")도 약화된다 — `.success`는 적용 완료가 아니므로, 실질 방어선은 다음 액션 읽기의 자가 검증이다(문언 보정 — 갱신 시점 자체는 유지).
- 폴링 상한을 50ms 타임아웃 상수와 공유하지 않는 것은 의미가 다르기 때문이다 — 그쪽은 병적 정지 차단기, 이쪽은 정상 앱의 적용 지연 대기다. 값은 실측 유래이고 도그푸딩 조절값으로 열어 둔다.

## 검토한 대안

- **즉시 1회 읽기**: 실측 기각 — Notion 상시 헛스킵.
- **memo 재사용**: 쓰기 전 값과 비교하는 자기 확인이 되어 검증이 항상 통과한다(장식) — 기각.
- **검증 실패 시 그 액션만 스킵하고 계속**: 잔여 액션도 같은 이유로 실패하며 폴링 상한 × N의 큐 점유만 산다.
- **`.debug` 로그**: 도그푸딩 stream을 켜 둔 동안만 남아 재심사 입력이 소실된다(`.illegalArgument` 로그 레벨 결정과 같은 판단).
