## 결정

AX 전략의 클립보드 쓰기 편집(delete·change·yank)은 텍스트를 AX로 쓰지 않는다. **오프셋 계층이 계산한 범위를 `AXSelectedTextRange` 쓰기로 정확히 선택한 뒤, 오퍼레이터는 현행 그대로 `Cmd-X`/`Cmd-C` 1타를 위임**한다(하이브리드 — 위임 표는 [20260808_ax-delegation-table-single-driver.md](20260808_ax-delegation-table-single-driver.md)). 오퍼레이터 게시 전에 **선택 착지를 되읽어 검증**한다 — 쓴 범위와 읽은 범위가 일치할 때만 파괴 단계가 나간다(선택 쓰기는 비파괴라 검증 실패는 무동작 스킵으로 끝난다). change도 같은 형태이며 엔진의 Insert 전이는 그대로다. yank의 collapse는 `←` 대신 AX 캐럿 쓰기(범위 시작)로 정확화한다.

`AXSelectedText` 쓰기(= 순수 AX 텍스트 편집)는 D1에서 채택하지 않는다.

## 배경·근거 (왜)

- **클립보드 충실도가 보존된다.** 클립보드를 채우는 주체가 지금과 같은 앱(`Cmd-X`/`Cmd-C`)이라, 앱이 네이티브 표현(HTML/RTF/블록)을 함께 싣는다 — 동일 앱 `dd`+`p` 왕복도, 외부 앱 붙여넣기도 현행과 바이트 동일. 순수 AX 텍스트 쓰기는 우리가 플레인만 쓸 수 있어(리치 읽기→RTF 얹기는 앱 네이티브 포맷이 왕복되지 않아 실익 얇음) 수혜 밴드(Notion)에 정확히 꽂히는 서식 강등 회귀였다.
- **앱 undo 스택 등록이 보장된다.** `Cmd-X`는 네이티브 명령이라 항상 등록된다. 순수 AX 쓰기는 미등록 앱에서 `u`가 이전 편집을 되돌리는 조용한 파괴 위험이 있었고(설계 세션 검증 항목이었다), 이 결정으로 그 실측은 D1 게이트에서 **D2 거짓말 감지 입력으로 강등**된다.
- **구현이 대폭 준다.** 명시 클립보드 쓰기·`recordEdit` 순서 재배열(`recordAndWrite`)·2단계 쓰기의 부분 실패 처리·`Clipboard.write` changeCount 실측이 전부 불필요해지고, `PasteWiseResolver`는 현행 계약(게시 전 `recordEdit`, 델타-1) 그대로 재사용된다.
- 파괴 단계 직전의 되읽어 검증은 오프셋 계층 버그·앱의 범위 클램프·grapheme 조정을 **파괴적 편집에서 무동작으로** 강등시키는 유일한 런타임 방어다(비용: 동기 읽기 1회).
- 순서 안전성: AX 쓰기는 대상 앱 메인 런루프에서 동기로 끝난 뒤 반환하고, 이어 게시한 합성 이벤트는 같은 런루프에서 그보다 뒤에 소비된다 — "동기 쓰기 → 게시" 방향은 레이스가 없다(낡은 읽기 문제는 반대 방향 `post → 읽기`에서만 생긴다).

## 검토한 대안

- **순수 AX 텍스트 쓰기 (`AXSelectedText` 대입)**: 명분은 `Cmd-X`가 표준이 아닌 앱에서도 동작한다는 것 — 그러나 실측 없는 이론 밴드이고, 그런 앱(터미널·특수 에디터류)은 대개 AX 텍스트 요소를 신뢰성 있게 노출하지 않아 accessibility 전략 대상 자체가 아니다. **탈출구로 기록만 남긴다**: `Cmd-X/C`가 어긋나는데 AX 텍스트 쓰기는 되는 앱이 실측되면, 그 앱 한정으로 순수 AX 텍스트 쓰기를 additive로 연다(그때 undo 등록·플레인 강등·명시 클립보드 쓰기 설계가 함께 필요하다).

수용한 단점: 편집의 실패 신호가 약해진다(`Cmd-X`는 오류를 안 돌려줘 실보고는 범위 쓰기에만 남음 — 파괴 단계가 네이티브 명령이라 실패 모드 자체가 온화한 것으로 상쇄), 비-QWERTY 치환 의존이 편집에 유지된다(역조회로 이미 해소 — 병적 레이아웃만 보류), D2 거짓말 감지의 순수 텍스트 쓰기 표본이 없어진다(범위 쓰기 표본은 남는다).
