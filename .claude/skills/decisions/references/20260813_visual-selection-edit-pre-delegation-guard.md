# AX Visual 세션의 `.selection` 편집은 위임 직전 선택 재검증

- **결정일**: 2026-08-13

## 결정

**AX로 고정된 Visual 세션**에서 `.edit(op, .selection)`(Visual `d`/`y`/`c`)을 위임(`Cmd-X`/`Cmd-C` 1타)하기 **직전에 선택을 1회 재읽어 검증**한다 — 기존 자가 검증 술어(앵커 쪽 끝 + pid 일치 + 선택이 비어 있지 않음) 재사용, 불일치·읽기 실패면 정직한 스킵(`.skipped`)이다. keyboard 세션은 현행 그대로다(게시된 키가 만든 선택 — 기존 위험 등급, D2 신설 아님).

## 배경·근거 (왜)

- 독립 검토가 "프로브 오판에도 파괴는 없다"를 이 축에서 반증했다: Visual의 AX 범위 쓰기(`.ax` 케이스)는 뒤에 게시가 없어 되읽어 검증이 없고, 설계된 실질 방어선은 "**다음 Visual 액션** 읽기의 자가 검증"이다. 그런데 `.edit(op, .selection)`은 Visual 매퍼 액션이 아니라 읽기 없이 맨 `Cmd-X`로 나간다 — 방어선이 정확히 파괴 단계 앞에서만 비어 있다.
- 앱이 우리가 쓴 범위를 **어긋나게 적용**하는 것은 실측된 축이다: TextEdit의 범위 클램프(세션 경로 pin 결정의 근거), Notion의 블록 경계 재해석, 그리고 외부에서 설정된 selection을 자기 문서 모델로 재정규화하는 Electron 에디터 관행. 그 위의 `Cmd-X`는 **앱의 선택**(우리 의도보다 크거나 다른 범위)을 자른다. `V`+`j`×n 뒤라면 규모가 문단 단위다.
- auto가 기본값이 되면 이 앱군이 사용자 opt-in 없이 자동 편입되므로, 명시 `strategy: accessibility` 시절의 위험 예산("사용자가 지시했다")이 더 이상 성립하지 않는다.
- 비용은 Visual 편집 1건당 읽기 1회(웜 ~0.03–7ms)다. 술어·상태가 전부 기존 것이라 새 기계가 없다.

## 검토한 대안

- **모든 Visual AX 범위 쓰기에 수렴 폴링(하이브리드 동형)**: 확장 액션마다 최대 40ms — 파괴 직전 1회 가드로 충분한 것에 비해 과하다. 기각 (도그푸딩에서 가드 불일치가 잦으면 재검토).
- **방치 (초안)**: 파괴 축이 열린 채 auto 기본화. 기각.
