# 캐시 충분성 1차 확정 — 콜백은 캐시만 읽어도 된다

## 결정

탭 콜백이 **캐시만 읽는** 형태를 유지한다 — 키 입력 시점에 라이브 AX 읽기를 섞을 이유가 실측에서 나오지 않았다. [콜백 경량 불변식](20260725_callback-light-invariant.md)이 실기기 검증으로 위임한 확인 항목 ②의 이행이며, 캐시가 담는 값은 계열 하나로 충분하다는 것도 함께 확정한다.

## 배경·근거 (왜)

콜백 경량 불변식은 "콜백은 캐시만 읽는다"를 설계로 못 박으면서, **그 캐시가 실제로 충분한지**(= 라이브 읽기가 필요한 케이스가 실기기에 있는지)는 리졸버가 붙은 뒤 도그푸딩으로 확인하라고 남겨 두었다. 단계 3 세션 2의 8항목이 그 입력이다.

**갱신 경로 2종이 실기기에서 살아 있다**:

- 앱 활성화 알림 — TextEdit ↔ Finder ↔ Chrome ↔ VS Code ↔ Notion ↔ Slack ↔ KakaoTalk 전환에서 매번 전이 로그가 찍혔다.
- `AXObserver`의 포커스 변경 — **앱 내부** 포커스 이동도 잡힌다. Chrome에서 옴니박스(`.textField`) → 페이지 본문 클릭(`.textArea`), Finder에서 리스트(`.nonText`) → `Cmd-F` 검색창(`.textField`)이 각각 전이로 관측됐다. 앱 전환 없이도 캐시가 따라온다는 뜻이라, "캐시는 앱 단위로만 정확하다"는 우려가 실측으로 기각됐다.

**등록 실패는 실사용 앱에서 0건이었다.** 세션 중 남은 `AXObserver 생성/등록 실패`는 시스템 권한 경고 다이얼로그(`universalAccessAuthWarn`)와 이미 종료된 pid뿐이다. 실패해도 앱 활성화 경로가 남아 폴백보다 나쁘지 않다.

**캐시가 담는 값이 계열 하나로 충분한지**: 8항목 어디에서도 "그 키를 판정하려면 지금 캐럿·선택 범위를 알아야 한다"가 나오지 않았다. 걸러내기 판정은 전부 계열만으로 갈렸고, 정확도가 아쉬웠던 지점들(경계 포화, 소프트 랩, Visual 후진)은 **판정이 아니라 시퀀스**의 문제이며 이미 M5 AX 읽기 혼용 몫으로 분류돼 있다. 즉 라이브 읽기가 필요해지는 시점은 "무엇을 걸러낼까"가 아니라 "정확한 오프셋으로 무엇을 지울까"로 넘어갈 때다.

**"1차" 확정인 이유**: 이 판정의 범위는 Keyboard 어댑터의 걸러내기다. M5에서 AX 읽기 혼용(`AXValue`·`AXSelectedTextRange`로 오프셋 계산)이 들어오면 캐시가 담을 것이 늘어나고, 그때 이 문서를 다시 열어야 한다. 그 확장은 [strategy-dispatch.md](../../architecture/references/strategy-dispatch.md)의 미결 질문으로 이미 열려 있다.

**함께 드러난 한계 1건**(캐시 충분성과는 별개): 캐시가 최신이어도 **아직 채워지지 않은 순간**이 있다 — 앱 전환 직후 ~20ms. 그 창은 캐시를 라이브 읽기로 바꿔서가 아니라 [미확정 창](20260801_unresolved-window-after-app-switch.md)으로 닫았다. 콜백이 여전히 캐시만 읽는다는 사실은 그대로다.

## 영향 범위

- 콜백 경량 불변식의 확인 항목 ②가 닫힌다 — 남은 위임 항목은 3ms 캡 재계측(이미 [캐시 형태 결정](20260801_focused-role-cache-shape.md)이 이행, `strategy: auto` 프로브의 supersede는 M5로 보류)
- 코드 변경 없음 — 현행 배선의 확정이다
